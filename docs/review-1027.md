## 二、P1:C(CNT)区地址缺 `0x8000` 前缀 —— **计数器静默落到定时器**(亲验·组帧对拍)

### 2.1 现象(亲验)

```python
build_area_read(..., FinsAddress("T", 10, None), 1, False) -> 800002000200000000110101 89 000a 000001
build_area_read(..., FinsAddress("C", 10, None), 1, False) -> 800002000200000000110101 89 000a 000001
                                                                    ↑区码 0x89  ↑字地址 000a
                                    T 与 C 的整帧 **逐字节相同 = True**
```

位访问同理(两者区码均为 `0x09`、地址 `000a`)。

### 2.2 手册实核(该切片的核心贡献)

| 手册位置 | 原文 | 含义 |
| --- | --- | --- |
| §5-2-2 **印刷 165** 地址表 | TIM 行 `000000 to 0FFF00`;**CNT 行 `C0000 to C4095 = 800000 to 8FFF00`** | T 与 C **靠地址最高位区分** |
| §5-2-2 **印刷 166**(PV / 完成标志行) | CNT 行同为 `800000 to 8FFF00` | 读 PV 与读完成标志**都带前缀** |
| §5-3-2 **印刷 173**(区码表) | TIM/CNT **合并为同一条**(位 `09` / 字 `89`) | **区码本身不区分定时器/计数器** |

**结论**:区码不分,唯一区分手段就是地址里的 `0x8000` —— 而本库不发这个前缀。

### 2.3 根因:手册 与 两大参考实现 分歧,本库跟随了参考实现

- 代码自述(`constants.py` 的 C 区条目):W342 的 CNT 行"字面带 `0x8000` 前缀",
  而 **C 语言参考实现与 Python `fins` 两大参考实现均只按码区分、不加前缀**;
  本库**跟随参考实现**,并把它登记为真机核证项;
- **本轮子代理的裁决意见**:**以手册为准**(手册已给出确定结论,参考实现恰恰是错的),
  且指出模拟器按无前缀实现,**不能作为佐证**。

### 2.4 我的裁决(明确表态)

**我同意子代理,但该条应由你裁决**,理由如下:

1. **依据铁律的优先序**是本项目自己定的:"协议实现必须有 `docs/protocol/` 收录的**官方文档**依据"
   —— 手册已给出**表级、双行(TIM/CNT 对照)一致**的依据;参考实现**不是**本项目的依据来源
   (尤其那两个参考实现**不在库内**,连复核都做不到,见 §三 P2-2 同族问题);
2. 该缺口的后果符合项目红线定义:**静默错值**(计数器读写落到定时器,返回值仍是合法 16 位 PV,
   无任何异常可察觉),而不是"拒绝合法操作";
3. **但保留一处诚实的不确定**:两个独立参考实现同时"不加前缀",可能反映**部分机型/固件**
   并不要求前缀(例如机型差异或旧系列)。因此**修法建议"按手册加前缀 + 真机复核"**,
   而不是"确定参考实现错"。

### 2.5 修法建议

- `codec._address_bytes`(起始地址 3 字节组装处)**与** `read_batch`/`random_*` 的多区条目组装处
  (`omron.py` 对应行)**同改**:`area == "C"` 时 `word |= 0x8000`(位/字两条路径都要);
- `address._check_area_max` **保持** `0~4095`(前缀是编码层语义,不进地址解析);
- **必须同步重锚测试**:`test_fins_clients.py` 中 T/C 相关用例目前只断言"与**库自身**建帧相同"
  —— 这属**自指断言**,会把错行为一并锁死(与 review-1025 §8.2 同型);golden 样本同理需重生成;
- `constants.py` 的 C 区条目与 `real-machine-checklist.md` 的措辞由"待终裁"
  改为"**按手册先修 + 真机复核**";
- README 待补表补登该条(§三 P3-14)。

## 三、P2:两条

### 3.1 P2-1 结束码 bit7(致命 CPU 单元错误)被判为"正常完成"(亲验)

- **亲验**:

  | 结束码 | 现判定 | 手册含义(§5-1-3 印刷 155 Note) |
  | --- | --- | --- |
  | `0x0000` | 正常 | 正常完成 |
  | `0x0040` | 正常 | **bit6 = 非致命错误** |
  | **`0x0080`** | **正常**(❌) | **bit7 = 致命 CPU 单元错误** |
  | **`0x00C0`** | **正常**(❌) | bit6+bit7 同时置位 |

- **代码**:判定式 `end_code & ~0x00C0 == 0` —— 把 bit6 **与 bit7 一并**视为可接受;
- **手册口径**:印刷 **162** 原文「Basically, the end code of a sent command that is completed
  normally is **0040**」—— 手册只把 **bit6** 与"正常完成"并列举例;
- **影响**:PLC 处于**致命错误**(CPU 已停)时,本库**按成功交付数据**,上层无法区分
  "数据有效"与"CPU 已停" —— 属**静默错值**形态(数据可能来自停止前的最后状态);
- **修法**:仅放行 bit6(`0x0040` 口径),bit7 走 `DeviceError`(或至少在返回值/`last_error` 中带出致命标志);
  若维持现状,**必须在 docstring 写明依据**(目前无)。

### 3.2 P2-2 FINS/TCP 封装的证据链失真 + 常量层零标注

- **现象 A(标注)**:**FINS/TCP 封装同批常量**(魔数 `FINS`、头长、命令 0/1/2、握手请求/响应长度)
  在 `constants.py` 中**无任何「待核/待补」标注**;而 `codec.py` 同段**已标**「依据待补」
  → **同一协议面两处标注不一致**(历史发现成立);
- **现象 B(证据链)**:`constants.py` 称 `fins_tcp_handshake_001.json` 为"**真机黄金样本**",
  但该样本实为**仓库自带独立实现脚本生成**(`tests/golden/generate_fins_samples.py`),
  真机清单只记"第三方模拟器网关 ✓";
  另其引用的 `fins_io.c L311` **本地不存在**(全仓仅注释引用);
- **依据状态**:W342 **完全不含** FINS/TCP 封装(子代理全文检索 `FINS` 魔数、`9600` **零命中**)
  —— 该段**无官方依据**,本就落在「待补」区;
- **影响**:该段唯一的"实证"被当作真机证据,会让后续复审**高估其可信度**;而"参考源不可复核"
  使裁决无法复算(与 review-1026 §6.1-4 同型);
- **修法**:①7 个封装常量统一加「依据待补(W342 不含 FINS/TCP 封装)」;
  ②文案改为"仓库独立实现生成的样本 + 参考实现交叉";
  ③README 待补行注明"未经真机/官方手册验证、参考源未入库不可复核"。

## 八、虚警留痕(本轮排除的疑点)

| 疑点 | 排查结论 |
| --- | --- |
| 一度疑「`C` 区缺前缀会让**客户端层**地址校验也越界」 | **不成立**:`read("C4096")` 在**客户端层**即被拒(区上界 4095),越界面不存在;问题纯在**编码层**不加上前缀(§二) |
