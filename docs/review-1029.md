## 二、P1-1:MC 的 `B`/`W` 按**十六进制**解析 —— 静默读写到另一只软元件(亲验)

### 2.1 现象

```
INOVANCE_MC_DEVICE_CODES:  X(0x9C,1,16) Y(0x9D,1,16) M(0x90,1,10) S(0x92,1,10)
                           B(0xA0,1,16) D(0xA8,0,10) W(0xB4,0,16)
                                                  ↑ base=16

实测换算:  B10 -> 编号 16      W10 -> 编号 16      (十进制应为 10)
对照:      M10 -> 编号 10 OK   D10 -> 编号 10 OK
```

### 2.2 手册实核(子代理)

| 手册位置 | 原文 | 含义 |
| --- | --- | --- |
| H5U 自印 **110**(§6.2.1) | `B0~B32767 **32768点**` | 点数只在**十进制**下自洽(十六进制应写 `B0~B7FFF`) |
| H5U 自印 **111**(§6.2.2) | `W0~W32767 **32768点**` | 同上 |
| H5U 自印 **661**(§16.4 MC 支持表) | `B0~B32767 32768点` / `W0~W32767` | 同上;**全表仅 X/Y 标「8进制编码」**,其余未标即十进制 |

**关键区分**:`X`/`Y` 的 `base=16` 是**正确的** —— 手册明确标 X/Y 为**八进制**,
代码在 `mc.py` 里把八进制编号转成帧内十六进制串(`X17 → 0x0F`),这与三菱 MC 惯例一致。
**问题只在 `B`/`W`** —— 它们既非八进制,也非十六进制,而是十进制。

### 2.3 旁证:同库 Modbus 路径就是十进制

`constants.py` 的 Modbus 换算表 `("B",(0x3000,32768))` 对应 H5U 自印 **418**
`B0-B32767 → 0x3000-0xAFFF`(**32768 个连续地址**)—— 十进制。
→ **同一文本地址 `B10` 在两条走线上指向不同元件**:Modbus 路径 = 元件 10;
MC 路径 = 元件 **16**。这是**库内自相矛盾**,而不只是"手册 vs 实现"。

### 2.4 影响与修法

- **影响**:`B10`→汇川 B16、`B1F`→B31、`B100`→B256、`W10`→W16 ——
  **静默读写到另一只软元件,无异常、无告警**;仅当编号大到溢出(`B32767`→206695)
  才由 PLC 以 4031 拒。属项目红线定义的**静默错值**。
- **修法**:`INOVANCE_MC_DEVICE_CODES["B"]/["W"]` 的 base 改 **10**;
  **若真机证实 MC 服务器确按十六进制解释 B/W**,则须**反向修正 Modbus 侧 B 的十进制口径**
  —— 两者必居其一,现状不可接受。
- **测试**:`test_inovance_mc_clients.py` 里 `B`/`W` **零用例** ——
  缺陷区**恰好没有断言**。补 `sent[15:19]` 字面量(`B10`→`0a 00 00 a0`)。
- **真机**:清单登记「B/W 帧内进制」。

## 三、P1-2:`read_range` 只校验**起始编号** —— 静默跨软元件读(亲验)

### 3.1 现象(实测帧尾)

| 调用 | 发出的 FC/地址/数量 | 越界的含义 | 结果 |
| --- | --- | --- | --- |
| `read_range("X1777", 2, "bool")` | `FC01 @0xFBFF 数量 2` | X 区上限 = `0xF800+1023 = 0xFBFF`;下一地址 `0xFC00` = **Y0** | **接受,零报错** |
| `read_range("X1770", 10, "bool")` | `FC01 @0xFBF8 数量 10` | 末 2 点落 **Y0/Y1** | **接受** |
| `read_range("S4095", 2, "bool")` | `FC01 @0xEFFF 数量 2` | S 区上限 `0xEFFF`;下一地址 `0xF000` = **T0 接点** | **接受** |
| `read_range("Y1777", 2, "bool")` | — | `0xFFFF+2` 撞 Modbus 地址空间上限 | **`ValueError`**(唯一被拦的) |

**唯一被拦的那例恰好说明拦截纯属巧合**:拦的是"起始 + count 超过 65535"(Modbus 全局上限),
**不是**"超过该软元件的编号上限"。

### 3.2 根因

- `_InovanceBase.read_range` 只翻译**起始地址**后委托 Modbus 层;
- Modbus `read_range` 只校验全局地址上限与单笔 FC 上限,**无按软元件的编号上限**;
- 汇川的编号上限只经 `to_modbus_address → _check_number` 对**单点**生效。

### 3.3 影响与修法

- **影响**:静默返回**别的软元件**的值(X 位跑到 Y 输入;S 跑到 T 接点),
  调用方按设备名记账 → 控制逻辑错。同类溢出(本机不拒、交 PLC 裁决)还有
  `M8511+x`、`C255+x`、`B32767+x`、`SD1023+x`、`R32767+x`、`T255+x`(32 位)、`D8511+x`(32 位)。
- **修法**:`_InovanceBase.read_range` 在翻译前按 `INOVANCE_BIT_DEVICES/WORD_DEVICES`
  的 `(base, limit)` 校验「起始编号 + count(× width) ≤ limit」,越界**入参期 `ValueError`**
  (X/Y 用八进制解析后的十进制编号参与比较)。
- **测试**:补 4 例 —— `X1777×2`、`X1770×10`、`S4095×2`、`Y1777×2`。

## 五、P2:两条

### 5.1 `C` 记号的 BOOL 区间读与单点**分叉 62464**(披露不足)

- **实测**:`read_range("C255", 2, "bool")` → `FC01 @255 数量 2`(= **Modbus 线圈 255**);
  而 `read_bool("C255")` → `FC01 @62719`(= 汇川 C255 接点)。**同一记号两条路径差 62464**。
- **根因**:`translate_batch_address` 先判 `is_modbus_address("C255")` → 真(`c` 前缀)→ 原样放行;
  汇川 `C` 在 `_INOVANCE_ADDRESS_RE`,Modbus `c` 在 `_PREFIX_RE`。
- **判定**:这是项目**已拍板**的「Modbus 记号优先」取舍,并已在 `address.py`/`inovance.py` 披露;
  但 `read_range` **自己的 docstring 完全未提 `C`**,且 `read_range` 的 BOOL 分支**零用例**。
- **修法**:`read_range` docstring 补 `C` 说明与例子;补一例把两条路径的分叉**显式锁死**。

### 5.2 `mc.py` 点数上限的**列归属描述错**

- `mc.py` 把 §16.4 表的「ASCII / 二进制」两列误读成「Q/L 口径 / iQ-R 口径」;
  经 `extract_tables()` 复核,表头列序为
  `操作名称 | 指令 | 子指令 Q/L系列 | 子指令 iQ-R系列 | 访问点数 ASCII | 访问点数 二进制`:
  **3584 = ASCII、7168 = 二进制**,而 Q/L/iQ-R 是**子指令**两列(0001/0003)。
- **影响**:仅注释,但按"Q/L 口径"自我设限会**白丢一半点数**(本库二进制走线)。
- **修法**:改为「ASCII 1~3584 / 二进制 1~7168,与子指令两列无关」。
