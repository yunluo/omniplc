## 二、P2:`T`/`C` 与 `X`/`Y` 位基址相同 —— **同编码、PLC 侧无法区分**(亲验)

### 2.1 现状

```
_BIT_BASE:  C 0x600   T 0x600        ← 同址
            X 0x1000  Y 0x1000       ← 同址
_BIT_SEGMENTS:  C ((0,511),)   T ((0,511),)     ← 段也相同
                X ((0,2047),)  Y ((0,2047),)    ← 段也相同
```

**实测**:`encode_bit_address(parse("T0")) == encode_bit_address(parse("C0")) == 0x600`;
`X0`/`Y0` 同为 `0x1000`;`T100`/`C100` 同为 `0x700`。
即**两个记号产生完全相同的 CMD + 地址**,编解码层**无法区分**。

### 2.2 论证与定级

- **这不是必然的缺陷**:同址项**已在 `docs/real-machine-checklist.md` 与 `docs/todo.md` 登记**(§6.5 订正了"README 待补表"的错误归属)
  "①…②PC10…(含 X/Y 与 T/C 同址问题)"—— 说明**项目已意识到**这是待真机/待手册裁决项;
  TOYOPUC 的位地址空间本身可能是**共享/别名**的(同族日系 PLC 存在 X/Y 与 T/C 共用编号空间的情形)。
- **但存在两处缺口**:
  1. **披露不完整**:`docs/protocol-features.md` §15 的 TOYOPUC 功能表**完全未提**同址/别名;
     现场按"T 是定时器、C 是计数器"的常识读 `T0`,可能实际读到**另一个软元件**;
  2. **无守卫**:解析器不区分两者,用户**无法表达**"我确定要 T 或 C" —— 若真机上两者本可区分
     (如靠不同 CMD),则本库**永久无法访问其中一个**。
- **定级 P2**(需真机/手册裁决;影响是"可能静默读到另一软元件",但**已在待补表登记**,
  非未披露的未知风险)。**若产品口径要求支持 T/C 各自独立访问,则升 P1。**

### 2.3 修法建议(与裁决解耦)

- **文档面(零风险,可立即做)**:`protocol-features.md` §15 增加一行
  「位地址别名:`T`≡`C`、`X`≡`Y`(同基址同段,`encode_bit_address` 实测同编码);
  待手册/真机裁决是否应分离 —— 见待补表」;
- **接口面(需裁决)**:若手册证明应分离,则在 `_BIT_BASE` 拆开并为旧写法保留别名映射
  (属**行为变更**,须 CHANGELOG 披露);
- **不建议**:在无手册依据时**猜测**分离基址(违反"不得臆造帧格式"铁律)。

## 三、P2:十六进制解析下的**静默偏差** —— 非零填充写法会落到另一段而非报错(亲验)

### 3.1 现状(设计明示,非实现错误)

- `ToyopucAddress.number` 的 docstring 明示:**"编号整数(十六进制换算,如 `"D0100"` → `0x0100`)"**
  —— 即**地址一律按十六进制解析**,这是**有意设计**(与三菱/松下不同);
- 但实现**不要求零填充**:`int(number_text, 16)` 接受 `"2047"`、`"10"`、`"100"` 等任意宽度。

### 3.2 实证:56 个样本"接受但编号 ≠ 十进制序号"

| 样本 | 用户按十进制的意图 | 实际编号 | 后果 |
| --- | --- | --- | --- |
| `C10` | 10 | **16** | **设计明示**(十六进制),文档已说明 |
| `L10` / `M10` / `K10` | 10 | **16** | 同上 |
| **`L2047`** | 2047 | **8263** | ⚠️ **危险**:8263 落进 L 段表**第二段** `(4096,12287)` → **被接受**,读到完全不同的软元件 |
| **`M2047`** | 2047 | (8263) | ✅ **被拒**("编号越界:超出该区上界")—— 因 M 的位段上界为 2047 |
| `X2047` / `Y2047` / `C255` / `T768` / `V100` … | — | — | ✅ 均被拒 |

**关键对比**:`L2047` **接受** vs `M2047` **拒绝** —— 同一类"未零填充的十进制写法",
一个静默错读、一个响亮拒绝,**行为不一致**,而差异来自段表的**稀疏性**
(`L` 位段为 `(0,2047)` + `(4096,12287)`,中间 2048~4095 **空洞**;
`0x2047 = 8263` 恰好跳过空洞落进第二段)。

### 3.3 论证与定级

- **根因是设计选择**(十六进制),**不是 bug**;但**后果**是"用户写错时**有时**静默错读、**有时**报错",
  取决于该区段表是否稀疏 —— 这种**不确定性**才是风险。
- **定级 P2**:需要用户先犯错才触发,且 `protocol-features.md`/模块 docstring 已声明十六进制口径;
  但"静默错读"在本项目的红线里属高危形态,且**低成本可缓解**。

### 3.4 修法建议(不改变协议语义)

1. **零填充校验(推荐,可开关)**:在解析时若编号文本**长度与区惯例不符**(如位软元件惯例 4 位)
   且值落在"非第一段",则**拒绝**或**记 warning**。
   注意:不能一律要求 4 位(`D100` 这类常见写法必须继续可用),故应**只对稀疏段区**加约束;
2. **文档面**:在 `address.py` docstring 与 `protocol-features.md` §15 明确
   "编号按十六进制;**请使用零填充(如 `L2047` 请写 `L2047` 表示 0x2047,若要十进制 2047 请写 `L7FF`**)"
   —— 用**例子**消除歧义,比抽象说明有效;
3. **测试面**:为稀疏段(`L`/`M` 的第二段)补**边界用例**,把"哪一侧接受、哪一侧拒绝"写成显式契约
   (子代理的测试切片到位后并入本条)。

### 6.2 经核无问题(帧面切片,均亲验)

   位段右移 4 位即 `_PACKED_SEGMENTS`(各段 `end % 16 == 15`,右移无损)、
   位号 n ↔ 字索引 n>>4 ↔ 字节 2n 属**同一线性空间**;
2. **组帧 ↔ 解析互逆**:请求 `length = 1 + payload` 与响应 `len == 4 + length` 同口径;
   6 条命令黄金向量的长度自洽(20→3、21→4、1C/1E 单点→5、1D 双字→7);
3. **类型 ↔ 字宽 ↔ 命令**:BOOL→20/21、16 位 1 字、32 位 2 字、64 位 4 字;
   读侧 `words_to_bytes(LITTLE)+from_bytes("little")` 与 `words_to_value(LITTLE)` **同口径**,
   写侧与之互逆(实测 float 1.0→`00 00 80 3f`);
4. **上限三处一致**:512 字 / 1024 字节在 codec、`read_range`、字符串路径同值;
5. **坏帧路径与异常类型**(实跑):短帧/长度不符/FT≠0x80/CMD 不符/数据长不符 → `ProtocolFrameError` **且拆连**;
   `RC≠0` → `DeviceError` **不断线**(含未知码),码提取正确;
6. **TCP/UDP 差异**:TCP `recv(4)+recv(length)`(传输层读满恰好 size,无短读风险);
   UDP 单次 `recv(2048)` + 发送前 `drain()`(实测 `events=["drain","send"]`,aio 亦有对应用例);
   上限 2048 对最大合法帧 1029 有 2x 余量;
7. **陈旧帧窗口已披露**(`toyopuc.py` 注释 + `troubleshooting.md` + `architecture.md` + 测试);
8. **i18n**:27 条错误码文案 **100% 在 en 表**,`_()` 包裹齐全;
9. **`protocol-features.md` §15 与实现逐条一致**(仅缺 §6.1-19 的两条地址模型披露 + 第 8 项文书口径)。

## 八、横切层顺带发现:串口参数校验的 NaN/inf 缺口(亲验)

> 本族无串口走线,但主会话在推进横切层(传输层)审查时发现一处**与已修 P1 同型**的缺口;
> 尚未到传输层台账,先记于此,后续归入横切层报告。

### 8.1 现象(亲验)

`transport/serial.py` 的 `SerialConfig.validate()` 用 `if self.baud_rate <= 0` 判非法 ——
**`nan <= 0` 恒为 False**,故 NaN(与 inf)**穿透校验**:

```
SerialConfig(port_name="COM3", baud_rate=float("nan")).validate()          -> 通过
SerialTransport(SerialConfig(port_name="COM_NOPE", baud_rate=float("nan"))) -> 构造成功
  t.connect() -> ValueError: cannot convert float NaN to integer   ← CPython 文案,非库内 i18n 文案
```

- **可达性**:`baud_rate` 是**公共参数**(公开 dataclass 字段),且 `SerialTransport.__init__` 会调
  `config.validate()` —— 用户可从公共 API 直达;
- **函数内不一致**:同函数里 `data_bits`(`not 5 <= x <= 8`)与 `stop_bits`(`not in (1,1.5,2)`)
  **都能拒绝 NaN**,唯独 `baud_rate` 的 `<= 0` 不能;
- **同型已修先例**:review-1023 P1 即"`connect_timeout`/`receive_timeout` 的 `<= 0` 让 NaN/inf 穿透
  → 流入 `socket.settimeout`";该处已由 `ac7af9d` 用 `math.isfinite` 收口。

### 8.2 定级与修法

- **定级 P3(非 P1)** —— 与 review-1023 P1 的关键差别:**此处不泄漏 FD**。
  实测 `_serial` 保持 `None`:异常发生在 `port.baudrate = nan`(pyserial 内部转换阶段,
  在 `port.open()` **之前**),端口从未打开;
- **但仍是真实缺口**:①违反 `validate()` 的「:raises ValueError: 参数非法」契约(抛 CPython 文案,
  现场不可读);②同形态若将来出现在"先 open 后配置"的顺序里就会变成泄漏;
- **修法(一行,同先例)**:`if not math.isfinite(self.baud_rate) or self.baud_rate <= 0:`,
  并可顺带要求 `int` 类型。
