# 现场排障指南

> 面向现场工程师与上位系统开发:工业现场通信问题怎么定位、本库的可靠性
> 机制如何配合排障、哪些现象是设计行为而非故障。协议用法见
> [examples.md](examples.md),已知固件差异见
> [firmware-notes.md](firmware-notes.md)。

## 一、失败信息三件套

本库公开 API **不抛自定义异常**:读失败返回 `(False, None)`、写失败返回
`False`,原因落在客户端三个属性上,这是排障的第一入口:

| 属性                         | 内容                                                                    | 排障用法                                |
| ---------------------------- | ----------------------------------------------------------------------- | --------------------------------------- |
| `client.last_error`          | 最近一次失败的人类可读原因(支持 `set_lang("en")` 切英文)                | 先看这个——大多数问题一句就说清          |
| `client.last_error_category` | 失败分类(下表五类),语言无关                                             | 程序化告警分级,不建议对文本做字符串匹配 |
| `client.last_error_code`     | PLC 原始错误码(Modbus 异常码 / MC 结束码 / FINS 结束码等);`None` = 无码 | 拿原始码对照对应协议手册的错误码表      |

分类语义(`ErrorCategory`,映射规则见 `core/base_client.py` 的 `_categorize`):

| 分类        | 含义                                         | 现场建议                                                                                                           |
| ----------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `TRANSPORT` | 链路级故障:连接被拒/被重置/对端关闭/DNS 失败 | 查网线、交换机端口、IP/端口、防火墙;反复出现考虑物理层(接地/干扰/线缆老化)                                         |
| `TIMEOUT`   | 接收超时(请求发出但响应没回来)               | 设备响应慢、负载高或网络拥塞;对照下文「超时」节                                                                    |
| `DEVICE`    | PLC 明确返回错误码(**链路是好的**)           | 按码查协议手册:多半是地址不存在、CPU 模式不对、写保护                                                              |
| `PROTOCOL`  | 坏帧:长度/校验/回显不符、非预期帧型          | 抓包比对;`last_error` 里带原始帧十六进制转储,可与 Wireshark 逐字节对照;对照 [firmware-notes.md](firmware-notes.md) |
| `UNKNOWN`   | 未归类                                       | 带报文转储提 issue                                                                                                 |

各类失败下**库的自动行为**(`retries`/`write_retries`/心跳/退避的分工,
应用层无需也不应重复处理):

| 失败类别                       | 拆连?                                 | 自动重试?                    | 退避门控?                   | 应用层建议                                          |
| ------------------------------ | ------------------------------------- | ---------------------------- | --------------------------- | --------------------------------------------------- |
| `DEVICE`(PLC 报错码)           | 否                                    | 否(链路是好的,重试无意义)    | 否                          | 修地址/模式/参数后由下一笔事务自然恢复              |
| `TIMEOUT`(接收超时,0 字节已读) | TCP 拆连重同步;UDP/串口整包语义不断线 | 按 `retries`/`write_retries` | 否(非建连失败)              | 查设备负载;写侧默认不重试防双写                     |
| `TRANSPORT` / `PROTOCOL`       | **是**(惰性重连)                      | 重连后继续                   | 建连失败推进指数退避门控    | 反复出现查物理层/多主站                             |
| 心跳探测失败                   | 同上口径                              | 下一 tick 自动重探           | 受门控约束(窗口内静默跳过)  | 看 `stats["heartbeat_fail"]` 与 `last_error`        |
| 监视器采集失败                 | 同上(共用客户端)                      | 下一周期自动重试             | 窗口内跳拍(`skipped_ticks`) | 看 `Monitor.stats` 与快照 `quality`(STALE 别当新值) |

## 二、按现象排查

### 1. 连不上(connect 返回 False)

- 构造参数先过一遍:`validate_endpoint` 在构造期就拒绝空 IP/越界端口;
  参数错误抛 `ValueError`,不会变成 `(False, None)`。
- **连接失败会进入指数退避门控**(默认开):基值 0.5s、倍率 2、上限 30s,
  附加随机抖动防「PLC 重启瞬间全网客户端一起砸连接」。门控激活期间
  重连尝试直接空转返回,`last_error` 保留**触发门控的那次真实根因**——
  别被后续的「失败」误导,要看第一次的原因。
- 当前还需等多久可读 `client.next_connect_in`(秒,`None` = 未激活);
  `client.reconnect_backoff = False` 可整体关闭门控(诊断期临时用)。

### 2. 时好时坏(间歇性故障,最难缠的一类)

现场经验:间歇故障大头在物理层——接地不良、变频器/干扰源附近的线缆、
受潮破损、交换机端口劣化。库侧能做的是**把趋势暴露出来**:

```python
s = client.stats
print(s["error_count"], s["last_rtt"], s["heartbeat_fail"])
```

- `error_count` 与 `last_rtt` 随时间缓慢爬升、RTT 逐渐变大 → 链路劣化
  趋势,优先查物理层与交换机;
- 心跳开启时 `heartbeat_ok`/`heartbeat_fail` 的比例变化是最早的劣化信号
  (心跳按 `heartbeat_interval` 默认 30 秒自动探测,仅对支持探活命令的
  驱动生效);
- 库的机制面(TCP keepalive、断线标记、惰性重连)保证间歇故障**不会
  停采**——如果采集停了,说明是持续故障,按「连不上」节查。

### 3. PLC 断电/重启后不恢复?

设计上不存在「不恢复」:传输失败即标记断开,下一次事务自动惰性重连;
心跳开启时连下一笔业务都不用等,心跳线程按周期自己重连(同样受退避
门控约束,不会形成重连风暴)。如果真的长时间不恢复:

- 确认 `reconnect_backoff` 没有被关闭后遗留下很长的门控窗口
  (读 `next_connect_in`);
- 确认设备侧:部分设备重启后需要重新握手/重新授权(如 FINS/TCP 握手、
  AB 的会话注册),这些库都会在重连时自动重做;若设备侧会话未超时释放
  (OPC-UA 的 "unclean exit" 会话是典型),需等服务端会话超时。

### 4. 超时频发(`TIMEOUT`)

本库对超时按链路形态区分处理,**排障动作也不同**:

| 形态                       | 库行为                | 现场含义                                                                   |
| -------------------------- | --------------------- | -------------------------------------------------------------------------- |
| TCP 接收超时               | 拆连(下一次事务重连)  | 迟到响应残留在 socket 缓冲,拆连正是防串帧的机制——**重连不是故障,是防串帧** |
| 串口部分字节后超时(帧截断) | 关闭串口重连重新同步  | 半包必然导致字节错位,必须重同步                                            |
| UDP/串口 0 字节超时        | **不拆连**,按重试继续 | 整数据报/无残渣,拆连反而造成慢链路上的重连抖动                             |

排查方向:

- `receive_timeout` 是否小于设备最坏响应时间(扫查周期长的老设备、
  网关型设备转发延迟都要算进去);超时是运行期属性,可直接改;
- 轮询是否过密(见第 8 节);
- 开 `set_debug` 看请求是否真的发出、响应是否真的没来。

**写重试双写警示**:`write_retries` 默认 0。超时只证明响应未到达,
写请求可能已被 PLC 执行——对计数累加、脉冲、步进指令这类**非幂等写**
开启写重试存在双写风险,仅覆盖写、位写等幂等写可安全开启。
`TransportTimeoutError` 的 docstring 有完整口径。

### 5. 坏帧/串帧(`PROTOCOL`)

- 坏帧异常**必带原始帧十六进制转储**(`last_error` 文本内),直接和
  Wireshark 抓包逐字节比对;
- 应答身份回显校验是常态:FINS 校验 ICF/SID/命令码回显、MC 串口校验
  路由回显、Modbus 校验功能码回显——回显不符通常意味着**串话/迟到帧**
  (多主站、两个客户端打同一从站、UDP 陈旧数据报),而不是线坏了;
  UDP 走线的陈旧数据报已由库在事务发送前自动排空(见第 7 节),
  TCP 走线靠超时拆连重同步——仍见回显不符优先查多主站;
- 同一链路出现多次坏帧后,优先怀疑:波特率/校验位不匹配(串口)、
  多个主站抢同一设备、网关转发剥帧。

### 6. PLC 返回错误码(`DEVICE`)

链路是好的,**重试无意义**——库对 `DEVICE` 类失败不断线、不重试,
原始码在 `last_error_code`:

- Modbus:异常码 01~0B,对照官方规范 V1.1b3 或
  [protocol-features.md](protocol-features.md) §1;
- 三菱 MC / 基恩士 KV MC:结束代码,对照三菱 SLMP 手册(SH-080008);
- 欧姆龙 FINS:结束码,库内置了中英文文本表(`FINS_END_CODE_TEXT`),
  `last_error` 直接给原因,如 `0x2108 数据不可更改`——**这条的现场
  实测根因多半是 `destination_network` 等路由参数与现场 CX-Programmer
  路由表不符**,逐项核对构造参数;
- 负数错误码是库内诊断码(本地缓冲/配置类问题,如 UDP 报文超长),
  不计入 `device_error_count`,含义见 `_extract_code` 注释。

### 7. 读到的值可疑(旧值/毛刺/互相干扰)

- **重试竞态窗口**:传输超时重试的间隙里,迟到的旧响应可能被当作本次
  应答消费(读侧拿到旧值的概率极低但存在)。写侧因此默认不重试
  (见第 4 节双写警示)。对旧值敏感的场景:读失败后不要用上一次的
  成功值凑数,`(False, None)` 就按无数据处理。
- **UDP 陈旧数据报(库已自动防护)**:UDP 一问一答走线中,上一事务
  超时后迟到的响应留在接收缓冲,下一事务会把它误当本轮应答——有身份
  回显校验的协议(FINS)按坏帧报错拆连,无事务号的协议(TOYOPUC/
  KV Host Link/MC 族 UDP/MEWTOCOL)则**静默读到旧值**。库在 UDP 事务
  发送前自动**排空接收缓冲**(黑匣子/调试日志可见"已排空 N 个陈旧
  数据报",被排的帧以 RECV 方向进黑匣子——夹在两次 SEND 之间的
  无主 RECV 帧就是它,属防护动作而非异常);排空与响应到达之间的
  极窄窗口仍可能漏进迟到帧(协议无事务号的最终防线只有应用层
  序号/时间戳),对旧值零容忍的场景在应用层加时效校验。
- **`last_error` 是实例级共享态**:多线程共用一个客户端实例时互相
  覆盖是设计行为。高频采集建议每线程独立客户端实例;
- **监视器与业务共用客户端**时,采集周期的失败会冲掉业务侧刚写入的
  `last_error`(共享同一本账)。建议 `Monitor` 独占客户端实例,
  语义见 `core/monitor.py` 模块 docstring。

### 8. 轮询把设备打满(PLC CPU 高/网络抖动)

- 优先**合并读**:`read_many`(多地址单类型)/ `read_range`(连续区段
  单事务)/ `read_batch`(驱动最优合并),N 个点位不产生 N 笔事务;
- 周期采集用 `Monitor`(后台线程按周期批量读 + 快照 + 变更回调),
  周期下限 0.05 秒是防误配;退避门控窗口内监视器自动跳拍
  (`stats["skipped_ticks"]` 可见),不会在设备恢复期补打;
- 变化才关心的点位用 `on_change` 回调,别在应用层全量轮询后自己过滤;
- 客户端并发模型是「同实例串行化」,吞吐不够时用**多个客户端实例**
  (连接池原语在路线图 `docs/todo.md`)。

### 9. OPC-UA 会话与订阅

- 本库订阅(handler + `create_subscription`)断线后句柄失效;构造选项
  `auto_resubscribe=True`(默认关)可让重连成功(显式/事务惰性)后
  **按订阅意图自动重建**(best-effort,单项失败记日志,重建结果以
  `active_subscriptions` 为准;`unsubscribe()` 才移除意图,断开保留);
  服务端 TransferSubscriptions 失败、订阅项 stale 各家服务器行为不一——
  重订是**全新订阅**(非 UA TransferSubscriptions 迁移),不踩各家差异;
- 重连后如果服务端拒绝(会话未超时释放),等会话超时后再试;
- TLS 相关不做(内网部署口径,项目红线)。

## 三、监视器的采集账(`Monitor.stats`)

与客户端的连接账(`ClientStats`)分立,排「采集侧」问题时看这本:

| 键                                  | 含义                             | 排障读法                                                     |
| ----------------------------------- | -------------------------------- | ------------------------------------------------------------ |
| `consecutive_fails`                 | 连续失败周期数                   | >0 且持续增长 = 采集持续失败,先看客户端 `last_error`         |
| `fail_count` / `cycle_count`        | 失败/总周期                      | 比例反映链路质量                                             |
| `slow_cycles`                       | 读取耗时超过 `interval` 的周期数 | 持续增长 = 周期配得太紧或链路太慢,调大 `interval` 或合并点位 |
| `skipped_ticks`                     | 退避门控窗口内跳过的拍数         | >0 说明期间发生过断线,配套看客户端 `stats`                   |
| `change_events` / `callback_errors` | 变更检测数 / 回调异常数          | 回调抛异常不会终止采集,但会记在这里                          |
| `last_ok_at` / `last_duration`      | 最近成功周期时间戳/耗时          | `updated_at` 长期不动 = 采集实际已停                         |

质量三态在快照里(`Monitor.get(tag_id).quality`):`INITIAL` 从未成功 /
`GOOD` 最新值 / `STALE` 失败期保留的旧值——**消费方必须检查 quality**,
拿 `STALE` 旧值当最新值是采集系统最常见的自伤。

## 四、报文级排障(`set_debug`)

```python
import omniplc
omniplc.set_debug(True)   # 进程级:所有协议收发报文十六进制转储
```

- 输出走标准 `logging`(logger 名 `omniplc.debug`),接自己的 handler
  落盘;`Monitor` 的组级异常、心跳异常也走这条通道(WARNING 级);
- 报错文案语言用 `omniplc.set_lang("en")` 切英文(默认中文),进程级;
- `set_debug` 是实时打印,进程崩溃后历史报文不保留——生产环境建议改用
  **报文黑匣子**(只存不打印,常驻无刷屏):故障后取最近报文逐字节比对。

```python
import omniplc

omniplc.set_frame_recorder(True)   # 常驻留存最近 1000 帧(容量可配,1~100000)
...
for rec in omniplc.recorded_frames():   # 故障后取现场(墙钟时间升序)
    print(rec.at, rec.direction, rec.label, rec.data.hex())
omniplc.clear_recorded_frames()    # 只清内容不关开关
```

黑匣子覆盖全部走线型协议(TCP/UDP/串口,与 `set_debug` 同一挂点);
会话型(OPC-UA/MX/MTConnect,操作级日志口径)无字节流不进缓冲。
与 `set_debug` 相互独立,推荐生产组合 = 黑匣子常驻 + 实时日志关闭。
