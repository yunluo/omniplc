# 已知固件/设备行为差异清单

> 同一协议在不同品牌、同品牌不同型号、甚至同型号不同固件版本之间,行为
> 并不一致——这是现场「换了备件就出问题」的常见根因。本清单收录本库
> **已知并在代码里处理过**的设备侧行为差异,每条给出现象、本库应对与
> 现场注意点。换备件、升固件后出现 `PROTOCOL` 类失败,先查本清单。
>
> **收录标准**:必须有实帧/真机核证或官方手册依据,并注明代码落点;
> 口径未定核的条目明确标「待核」。新差异按此标准增补。

## 1. AB / EtherNet/IP:写应答回显省略

- **现象**:个别服务端(用户联测实帧核证)对 Write Tag(0x4D)的应答
  首字节回 `0x00` 而非规范的「服务回显 | 0x80」。
- **本库应对**:对回显字节为 `0x00`(回显省略)放行;非零错误回显仍按
  坏帧拒。本库事务是同步一问一答,回显对请求-应答关联是冗余,放宽
  不引入错配风险。
- **落点**:`plc/ab/codec_cip.py`(`_parse_service_payload_with_status`
  附近注释「回显宽容」)。

## 2. 欧姆龙 NJ/NX:BOOL 数组双固件行为

- **现象**:NJ/NX 对 BOOL 数组元素路径的应答类型随固件不同:多数固件
  回元素类型 BOOL;个别固件回存储字类型 DWORD(按 Logix「下标 // 32」
  打包口径)。
- **本库应对**:先按元素直读;应答 DWORD 时自动回退按字读并移位取位,
  两种固件行为都覆盖,调用方无感。
- **落点**:`plc/omron/cip.py`(`_read_bool_array_element`)。

## 3. 松下 MEWTOCOL:应答站号「直连口径」

- **现象**:手册规定应答回显请求站号,但现场存在应答自报站号 `EE`
  (直连口径)的机型。
- **本库应对**:站号校验对 `EE` 放行,其余仍按回显校验。
- **落点**:`plc/panasonic/codec_mewtocol.py`(模块 docstring 与
  `_ensure_header` 的 `EE` 放行分支)。

## 4. 基恩士 KV MC(兼容 SLMP):`R` 位组记号编号口径【待核】

- **现象**:KV 的 MC 兼容模式里继电器 `R` 的线上编号口径存在两种理解:
  记号数字原样(`R515` = 组 5 位 15 → 发 515)或换算线性位号
  (`R515` → 95)。写错口径会**静默错址**(写到了别的点)。
- **本库应对**:按「记号数字原样」发送(与 KV Host Link 路径同字符串
  语义,2026-09-28 真机联测通过);不复核「位号低两位 00~15」。
  原引用 SH081257ENG 经证伪删除,协议手册待补,真机终核判据见
  [real-machine-checklist.md](real-machine-checklist.md) KV MC 条目。
- **现场注意**:上电前先用 `R` 位做一次写读往返,并在 KV Studio 里
  确认变化的点位与预期一致,再放量。
- **落点**:`plc/keyence/mc.py`(模块 docstring)。

## 5. 基恩士 KV Host Link:`.H` 读数据与出错码形状重合

- **现象**:`.H` 十六进制读的合法数据(值 `E0`~`E9`,如 `"E5"` = 229)
  与 Host Link 出错代码 `E0`~`E9` 形状完全重合,协议层无法区分。
- **本库应对**:`.H` 读路径跳过整条出错码判定,数据令牌交由 parse 层
  按格式校验(形状不符一样报坏帧,不会静默错值);其余格式正常查错。
- **落点**:`plc/keyence/hostlink.py`(`_transact` 的 `check_errors`
  参数 docstring)。

## 6. 欧姆龙 FINS:节点号惯例与路由配置

- **现象 1**:以太网 FINS 节点号惯例 = IP 地址末段,但 TCP 由握手分配、
  UDP 无握手,配置错节点号会得到难以理解的错误码。
- **本库应对**:节点号缺省自动——TCP 取握手分配值,UDP 从本机出口 IP
  末段推导(目标 = PLC IP 末段);显式配置原样使用不被覆盖。
- **现象 2**:`0x2108 数据不可更改` 一类错误码,2026-09-24 真机闭环
  实测根因是 **`destination_network`/路由参数与现场 CX-Programmer
  路由表不符**,而非写保护——库帧组装全合规。
- **现场注意**:报 FINS 错误码先逐项核对构造参数
  (`destination_network`/`destination_node`/`destination_unit`)与
  CX-Programmer 路由表,再怀疑设备;错误码文本表在
  `core/constants.py`(`FINS_END_CODE_TEXT`)。
- **落点**:`plc/omron/omron.py`(节点号推导)、`core/constants.py`
  (码表与范围常量)。

## 7. 读码器:触发/应答时序因型号而异

- **现象**:基恩士 SR 的读码应答在**关窗(LOFF)之后**才发;海康 ID 系
  串口的结果在扫描窗**内**即时流出。同一套「触发→读结果→停窗」时序
  不能通吃。
- **本库应对**:`KeyenceSrClient` 关窗后读应答;`HikrobotIdSerialClient`
  先读结果行再发停止文本,避免停窗截断解码。
- **现场注意**:混用品牌读码器时,先读各客户端 docstring 的时序说明,
  不要复制粘贴时序代码。
- **落点**:`plc/keyence/sr.py`、`reader/hikrobot_serial.py`(模块
  docstring「时序与基恩士 SR 的差异」)。

## 8. OPC-UA:会话恢复与订阅迁移因服务器而异

- **现象**:客户端断线后,部分服务器不及时释放会话("unclean exit"
  会话占位,重连被拒直到会话超时);重连后的订阅迁移
  (TransferSubscriptions)各家服务器成功率不一,失败时订阅项 stale。
- **本库应对**:重连由客户端惰性重连负责;订阅**不自动重订**(有意的
  生命周期简化)——连接恢复后由调用方重建订阅。自动重订选项在计划
  ([todo.md](todo.md))。
- **现场注意**:订阅丢失的表现是「连着但数据不再更新」——长周期场景
  建议消费方对数据新鲜度设阈值告警。
- **落点**:`plc/opcua/client.py`(订阅生命周期说明)。

## 9. Modbus:FC08 诊断非强制,探活支持面不一

- **现象**:FC08 诊断在规范中非强制,不少从站不支持——探活命令并非
  所有设备可用。
- **本库应对**:仅支持探活命令的驱动启用应用层心跳(`_has_ping`),
  MC 系无 0101 探测命令的帧型(1E/3C/4C)构造期即不启用心跳,置
  `heartbeat_interval` 也不会有线程运行;链路保持由 TCP keepalive 与
  事务期惰性重连兜底。
- **落点**:`core/base_client.py`(`_has_ping`、`ping_supported`)、
  `plc/modbus/modbus.py`(`_ping_probe` 注释)。

## 与固件版本相关的通用建议

- 同型号不同固件版本的协议行为可能不同(超时口径、错误码、可选命令
  支持面都会变),**换备件先核对固件版本**;换后出现 `PROTOCOL` 类
  失败,先查本清单与 [real-machine-checklist.md](real-machine-checklist.md),
  再抓包比对(坏帧报错自带原始帧转储)。
- 待核证条目随真机核证滚动迁出;新差异按顶部收录标准增补。
