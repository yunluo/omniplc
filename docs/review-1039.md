## 一、`aio` 层:架构实证(亲验)

### 1.1 实现方式

```
aio/__init__.py:233   ThreadPoolExecutor(max_workers=1, thread_name_prefix="omniplc-aio")
aio/__init__.py:252   async def _run(self, operation): ... await loop.run_in_executor(self._executor, operation)
```

即:**组合对应同步实例**,所有协议调用经**单线程**执行器串行执行 ——
协议编解码**只有一份代码**(与同步版线程安全语义一致)。

### 1.2 ★ 实测:三条关键声明全部成立

| # | 模块头声明(原文要点) | 实测 | 判定 |
| --- | --- | --- | --- |
| 1 | **同一客户端仍串行**;并发收益来自跨设备重叠等待 | 3 次 `_run` 的工作线程 tid = `[10620, 10620, 10620]`(**唯一**),主线程 tid=30272(**确实切了线程**) | ✅ 成立 |
| 2 | **无 asyncio 原生取消**:`wait_for` 超时只是放弃等待,**已提交的写事务仍会在工作线程里跑完** | 投递 `sleep(0.5)` 任务 → `wait_for(0.1)` 超时返回,此刻 `done=[]`;再等 0.7s → `done=[True]` ⇒ **任务确实跑完了** | ✅ 成立 |
| 3 | `close()` 关闸后**排空**已提交任务(不锯断在途事务),再释放线程 | 在途任务 0.4s 时调 `close()` → **耗时 0.36s**(≈ 剩余时长)⇒ **确实排空**;`close` 后 `done2=[True]`、任务结果可取;关闸后新提交 → `RuntimeError: 客户端已关闭,无法再执行协议操作` | ✅ 成立 |

### 1.3 文档诚实度(该层最值得肯定之处)

模块头**主动**写明"**这不是原生 asyncio 协议栈(预期管理)**",并逐条列出:
单线程语义、属性直读"不发报文也不切线程"、**无原生取消**、`close()` 排空语义。
对照本库其他层:`native/` 用 `pending` 标志 + 保守拆连实现**真取消**,
而 `aio/` **明确不假装**支持取消 —— 两种口径**各自如实披露**,无夸大。

> **建议(零风险)**:README「异步」节的入口若未同时点明"`aio` 层与 `native` 层是**两套不同取舍**"
> (`aio` = 覆盖全 34 客户端但**无真取消**;`native` = 真 asyncio + 真取消但**只覆盖 5 族**),
> 建议补一句选型指引 —— 这是用户最容易误判的一处(以为 `aio` 是 `native` 的超集)。

## 二、`aio` vs `native`:两套独立实现的分工(厘清)

| 维度 | `omniplc.aio` | `omniplc.native` |
| --- | --- | --- |
| 规模 | 2825 行,**35 个 `A*` 镜像**(实测) | 6438 行,**9 个客户端 / 5 族** |
| 机制 | **线程池桥接**(`max_workers=1` 同步实例) | **真 asyncio**(`AsyncBaseClient` + `AsyncTcpTransport`) |
| 取消 | ❌ **无原生取消**(如实披露) | ✅ `pending` 标志 + **保守拆连** |
| 覆盖 | **34/34 客户端全覆盖**(review-1033 §1.2 实测) | 5 族(Modbus/MC/FINS/汇川/S7) |
| 协议代码 | **与同步层共用同一份** | 独立实现(需逐条对齐) |

**判定**:两者**不是替代关系而是**"**广覆盖低语义**"vs"**窄覆盖高语义**";
`aio` 靠复用同步代码消除分叉风险,`native` 靠独立实现拿到真取消 ——
**但代价是 `native` 侧存在同步/异步分叉面**,本会话已实测到三处:
`native/melsec.py` 字符串门控同缺口(review-1028 §6.1)、
S7 取消语义未落地(review-1034 §4.2)、`_write_string` 写法分叉(review-1034 §五 P3-8)。

### 3.3 `native/transport.py` 的取消机制(与同步层的本质差异)

```
AsyncBaseTransport.pending  (:169)    ← 请求已发出但未收到应答
AsyncBaseTransport.mark_synced (:173) ← 收到应答后清除
```

`AsyncBaseClient` 在事务收口处检查 `transport.pending` ⇒ **已发请求的取消一律保守拆连**
(`native/base.py` 的 `if transport is not None and transport.pending: self._mark_disconnected()`)。
**这是同步层不存在的概念**(同步无取消),也是 `native` 相对 `aio` 的核心增值。

> ⚠ **已知未落地一处**:`AsyncS7Session` 从不置/读自身 `pending`,请求由**内层**
> `AsyncTcpTransport` 发出 ⇒ `_execute` 的判据查的是**会话对象**(恒 `False`)⇒
> S7 的取消退化为 `aio` 层语义(`connected` 仍 `True`,下一事务读到迟到应答报**假 PROTOCOL 错**)。
> **详见 review-1034 §4.2(P2-2)** —— 本节仅标注"机制存在但有一族未接上"。

## 五、P3:`aio` 层的**性能与并发陷阱未被量化披露**

模块头说明了"**同一客户端仍串行**""并发收益来自跨设备重叠等待",
但**未给出量级**,使用者容易误判:

- 一个客户端上的 N 个并发 `await` **不会**并行 —— 它们**排队**在同一个工作线程上,
  总耗时 ≈ **各次事务耗时之和**(而非最大值);
- 叠加 `aio` **无原生取消** ⇒ 用 `asyncio.gather` 扇出大量请求时,
  **取消整个 gather 不会缩短已排队任务的执行时间**(`close()` 还要**等它们全部跑完**);
- **修法(零行为风险)**:在模块头或 README「异步」节补一句量级示例
  (如"对同一客户端的 10 个并发读 ≈ 10 次事务串行耗时;要并行请用多个客户端实例"),
  并在 `close()` 的 docstring 点明"**关闸等待时间 ≈ 在途 + 已排队任务总时长**"。
