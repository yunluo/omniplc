## 二、P1:错误帧按 2 字符定长收包 —— 待核项①一旦成立即**级联失效**(亲验·端到端实证)

### 2.1 现状

- **模块头自认**(`codec_mewtocol.py:3-8`):
  「**待核** …①错误码疑 **4 字符**(类别 2 + 细分 2,如 `4004`/`4101`)而非 2 字符
  ——若属实 **TCP 须按 9 字节收否则残留脏缓冲**」;
- **实现按 2 字符**:
  - 解析 `parse_response`:`code = text[4:6]`(`:196`),`_ERROR_MESSAGES` 表键亦全为 2 字符(`:39-66`);
  - TCP 收包 `_transact`(`mewtocol.py:350-352`):
    ```python
    head = transport.recv(4)
    if head[3:4] == b"!": response = head + transport.recv(5)   # 恒 9 字节
    else:                 total = parse_expected_size(data_chars); response = head + transport.recv(total - 4)
    ```

### 2.2 实证(脚本化 TCP 流:一笔 4 字符错误响应 + 紧随一笔正常响应)

```
模拟缓冲流: '%01!400405\r%01$RD123412\r'

第 1 笔 -> (False, None)
           last_error="ProtocolFrameError:MEWTOCOL 响应未以 CR 结束:'01!40040'"
           消费 9 / 24 字节 -> 残留 15 字节

第 2 笔 -> (False, None)
           last_error="ProtocolFrameError:MEWTOCOL 响应未以 CR 结束:'$RD12341'"
           消费 22 / 24 字节
```

### 2.3 三重后果与定级依据

| 后果 | 说明 |
| --- | --- |
| ① 错误响应**退化为坏帧** | 设备明确报错(链路正常、应归 `DeviceError` + `last_error_category=DEVICE`)却报 `ProtocolFrameError`(PROTOCOL)；排障时看不到设备真因,还会触发**拆线重连** |
| ② **残留 2 字节** | 这正是模块头自己警告的"残留脏缓冲" |
| ③ **无法重同步** | MEWTOCOL **无事务号**(不同于 Modbus MBAP / MC 4E 序列号），一旦错位,**该连接上后续每一笔响应都是垃圾** —— 不是偶发,是**级联失效** |

**定级 P1 而非 P0 的依据**:触发条件是**待核项①为真**(需真机裁决);若真机为 2 字符则当前行为正确。
但**后果是级联失效 + 错误分类错**(非静默错值),且**修法无风险**见下,故按 P1 处理并要求优先裁决。

### 2.4 修法建议(与待核项①解耦)

**关键**:错误响应是**纯 ASCII 且以 CR 结尾**(错误码/文本不含 CR),因此
**改为"读到 CR 为止(带上界)"即可与错误码宽度无关** —— 即使真机宽度暂未裁决也不会踩雷:

- `mewtocol.py:351-352`:错误分支改成 `_recv_until_cr(transport, limit)`
  (逐字节或块读累积,遇 `\r` 停,超 `MEWTOCOL_MAX_LINE` 类上界即 `ProtocolFrameError`);
- `parse_response`:错误码取值改为"跳过 `!` 后到 BCC 前的**全部**字符"
  (即 `text[4:-3]`),`_ERROR_MESSAGES` 查找按"先全长、再前 2 字符"降级,
  避免 4 字符表未收录时丢信息;
- 同时保留 2 字符表并把 4 字符表作为**待补**(README「待补」已登记该族手册)。

**另有一条与①无关也成立的语义错报**:若真机确为 4 字符码,现实现会取前 2 字符查表 ——
`4004` 被报成 **40「BCC 错误」**、`6101` 被报成 **61「数据错误」**,
即**报出的是错误的原因分类而非细分**,方向性误导(`last_error_code` 亦随之错)。

## 四、P3:标注与文案

### P3-1 `address.py` 零「待核」标注(与其余三文件不一致)

- `codec_mewtocol.py`(4 处)、`mewtocol.py`(1 处)、`mc.py`(1 处)均标了手册未收录;
  **`address.py` 一处未标** —— 而它承载的是**地址记号与进制**这一协议面
  (接点区 `X/Y/R/T/C/L`、数据区 `D/L/F/S/K`、`L` 双语境、位号形式)。
- **影响**:后续维护者按文件翻依据时,会以为该文件的记号模型有手册支撑。
- **建议**:文件头补一句与三文件同款的「依据待核(手册未收录,见 README 待补)」。

### P3-2 报错文案给出的示例地址**本身不被解析器接受**

- `mc.py:86-88` 与 `:93-95` 的报错文案写「(如 `{}000F`)或点号形式(如 **`{}.15`**)」;
  但 `parse_mc_address`(`plc/melsec/address.py:33`)的正则要求**点号前必须有字号数字**:
  - `R.15` → `ValueError`(实测);
  - `R1.15` → ✔(`number=1, bit=15`)。
- **影响**:用户撞到该报错、照文案写 `R.15` → **再撞一次**同样的错 —— 文案把"无效形式"当示例。
- **建议**:文案示例改 `R1.15`(或 `R001.5`),并明确"点号形式须带字号"。

### P3-3 走线级「待核」项缺登记对照

- 模块头把"①错误码宽度 ②多字值字序"列为真机终裁项,但 `docs/real-machine-checklist.md`
  的松下行是否逐条对应,未在本切片核对(测试面切片回报后统一核对并登记)。
