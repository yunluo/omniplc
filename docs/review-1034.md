### 2.2 论证

- 档案**自称**是"事实底本"(它带"参考实现文件 + 函数 + 行号"级出处),且档案里写明
  "**供 `plc/siemens/codec.py` 实现就近引用**" —— 即**档案的设计意图就是被 §N 引用**;
- 实际却是:代码引用**库外的**源码行号,而**库内的**档案不被引用 ⇒
  **S7 的每一条帧面事实在库内都无法复核**;
- 且行号**自相矛盾**(同一函数三种行号):
  - `parse_response`:档案 §3 写 `L1523-1554`;`codec.py` 一处写 `L1523-1606`、另一处写 `L1536-1554`;
  - `build_setup_communication_request`:档案与 `codec.py:377` 写 `L373-398`,`codec.py:289` 写 `L379-398`;
  - `encode_address`:档案 §5 写 `L76-122`,`codec.py:407-409` 写 `L55-96`;
  - `L431-450`:档案 §10 判给 `_send_cotp_disconnect`,`codec.py` 判给 `_parse_cotp_cc`。
- **PDU 分片容量 18/35 的唯一出处** `client_base.py` **已随封装退役删除**(库内不存在)。

### 2.3 定级与修法

- **定级 P1**:与 review-1029(汇川"依据零就近引用")同型,但**更严重** ——
  汇川是"没引",本族是"**引了库外已删除的文件**"(表面有依据、实际可核性为零),
  且**行号互相矛盾**会让后续复核者做无用功。

## 三、P2:COTP DR 帧 `LI` 与实际字节数不符(且被测试固化)

### 3.1 现象(亲验)

```python
# client.py / native/siemens.py
struct.pack(">BBHHBB", 6, 0x80, dst_ref, SRC_REFERENCE, 0x00, 0x00)
#                    ↑LI=6 声明其后 6 字节,而实际有 7 字节(整帧 8 字节)
```

实测:`LI=6 但实际=8`。档案 §2 **只给 DR=`0x80`**、§10 只说"dst_ref 回显",**无 DR 布局依据**。

### 3.2 影响与修法

- **影响**:对端按 `LI` 切帧时,多出的第 8 字节会被当作**新 PDU 起始**(下一个 `LI=0x00`,非法)。
  因 DR 后立即 `tcp.close()`,**实际影响≈0**,但属"**坏帧自己发出去**";
- **测试固化**:**`test_siemens_s7_clients.py` 把该 8 字节形态写成黄金断言**
  (`b"\x06\x80\x00\x0a\x00\x01\x00\x00"`)⇒ **修缺陷必须先改测试**,否则测试会拦住修复;
- **修法**:改 `>BBHHB`(7 字节,`LI=6`);若参考实现同款,按"双向裁决"在档案 §2
  登记"**参考实现 DR 帧 LI 少计 1 字节,本库不照抄**"。

## 四、P2:会话层两条

### 4.1 `read_batch`/`read_many` 的多变量读**不受协商 PDU 约束**(同步/native 同病)

- **实测**:20 项 multi read 的**请求 S7 PDU = 252 B**、**应答 = 254 B**(按 DOUBLE 算),
  而协商 PDU 可为 **240**(老 S7-300/400 常见);
- **证据**:全库 `pdu_size` **只出现在 `read_area`/`write_area` 的分片处**;
  入参校验只有条目数(`S7_MAX_MULTI_VARS=20`);对照:同 PDU 下 500 B 的 `read_area`
  **正确分 3 帧**、满分片应答**恰 240 B**;
- **影响**:协商 PDU < ~252 的 CPU 上会发出**超协商值的 PDU**;PLC 反应(拒绝码/丢弃)
  **未经真机验证**,最坏是该 API 在这类 CPU 上**完全不可用**(功能失效,非数据污染);
- **修法**:按 `pdu_size` 规划分笔(请求 `12+12n ≤ PDU` 且应答 `14+Σ(4+len+对齐) ≤ PDU`),
  或在入参期显式 `ValueError`;并把结论补进档案 §10(该节**未登记多变量面**)。

### 4.2 native S7 的**取消语义未落地**(与文档明文冲突)

- **实测**:事务进行中 `session.pending=False` 而内层 `tcp._pending=True`;
  `task.cancel()` 后 `client.connected=True`(**未拆连**);
  下一事务读到迟到应答 → `S7ProtocolError:序列号回显不符:期望 3,收到 2`、**category=PROTOCOL**;
- **文档冲突**:`architecture.md`、`docs/async.md` 均声明"**已发请求 → 保守拆连**";
- **影响**:每个用户级取消(如 `wait_for` 超时)都会让**紧随其后的第一次无关事务凭空失败**,
  并被记成**假协议错**(下一次事务自愈);**无静默错值风险**(序列号强校验兜底);
- **修法**:`AsyncS7Session` 覆写 `pending` 委托内层,或在 `_transact` 内自置标志;补"取消 → 拆连"用例。
