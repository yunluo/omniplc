**研究过程留痕**(供下轮省时):MC 3E 请求域序 = 子头(2) + 网络号(1) + PC 号(1)
+ 模块 I/O(2) + 站号(1) + **数据长度(2,小端)** + 监视定时器(2,小端)
+ **命令(2,大端)** + 子命令(2,小端) + **编号(3,小端) + 软元件码(1) + 点数(2,小端)**
+ 写数据;响应 = 同前 9 字节头(子头 `D0 00`)+ 结束码(2,小端)+ 数据。
命令码常量为**"线上字节序 int"**(`MC_COMMAND_BATCH_READ = 0x0104` 即字节 `01 04`),
写 `to_bytes(2, "big")` 得正确线序 —— 此点 `constants.py:242` 注释已说明。

## 三、P3:客户端层观察项

### P3-1 离线状态下"参数非法"被连接失败遮蔽(全驱动同构,建议文档披露)

- **现象**(实测):客户端**未连接**时,`read_ushort("")` / `read_ushort("QQ1")`
  返回 `(False, None)` 且 `last_error` 是**连接失败**,而非"地址非法"的 `ValueError`;
  **同一调用在已连接状态下正确抛 `ValueError`**。
- **机制**:参数解析在 `_read` 内(操作体内),而 `_execute` 在进操作体前
  先做惰性重连(`core/base_client.py:1482` 之前);未连接且连不上 → 直接返回失败。
- **影响**:现场"地址写错 + PLC 未上电"同时发生时,调用方看到的是连接错误,
  容易先怀疑网络而不是地址 —— 排障方向被带偏。**不是契约违背**(库的契约是
  "参数非法抛 `ValueError`",而此处根本没走到参数校验),属**错误优先级**问题。
- **判断**:与 Modbus/其他驱动**同构**(参数解析普遍在操作体内),属全局形态而非本族缺陷;
  若要收口应统一到 `BaseClient` 层(需先解析地址再连接),改动面大、收益有限。
- **建议**:仅在 `docs/troubleshooting.md` 的"失败信息三件套"节补一句
  "**未连接时优先看连接类原因**;确认链路后再核地址参数",不提议改代码。

### P3-2 `_check_bit_device_word_access` 对未知软元件静默放行

- `melsec.py:186-189`:`except ValueError: return` —— 未知软元件不在此处报错,
  交由组帧路径的 `_device_info` 上抛(docstring 已声明该口径)。
- **核验**:实测 `read_short("ZZ1")` 仍能抛 `ValueError`(来自组帧路径),
  错误时机与文案一致 → **有意设计,非缺陷**。仅记录:该 `return` 使门控成为
  "尽力而为",若将来组帧路径改成不校验,门控会静默失效(建议加一行注释互锚)。

### P3-3 5 个品牌子类共用本族基类,`_bit_device_word_access_allowed` 语义靠类属性区分

- 基类默认 `False`(三菱口径:位软元件字访问须 16 点对齐,易错读);
  松下等按其地址模型覆写为 `True`。
- **核验**:实测三菱侧读/写/批量均拒(`M16`);品牌侧行为未在本轮展开
  (**未核实**,属 KV/汇川/松下各自切片范围)。
- **建议**:该属性是**跨品牌语义开关**,建议在 `plc/melsec/melsec.py:104-107`
  的注释里点明"哪些品牌子类覆写为 True 及其理由",便于后续维护者判断新增品牌该取哪一侧。

## 四、正面确认(本轮验证过的强度)

- **码表层**:28 个软元件、进制分组与实测换算一致、零重码、未知记号显式拒绝并列出支持集
  —— 这一层是 `L=0xA0` 那次 P0 的修复成果,5 个版本后未回退;
- **帧层路由**:帧型 × 走线白名单双向互斥,构造期拒绝而非运行期;
- **命令层**:0401/0403/0406 三大命令的**建帧与解析双向对表**;0406 的位块
  "1 点 = 16 位"(与 0403 位单位的半字节打包**不同**,注释已显式区分 —— 这是极易踩的点);
- **上限层**:120 块 / 192 点 / 2000 位 / 125 字等边界**精确顶格**;
- **防错层**:位软元件字访问、位号后缀、区域类型不匹配三条防线**读写批量三路径共用**;
- **帧结构校验**:`_locate_data` 同时校验响应头、长度域、4E 序列号回显、
  结束码(非 0 → `DeviceError`)、**尾部多余字节**(`ProtocolFrameError`);
- **不变量注释**:多处把历史修复的**理由**写在代码旁(如"1 点 = 16 位"与
  "半字节打包"的区别、"位软元件字访问会被 PLC 拒或按 16 点/字错读"),
  这是本项目文档纪律在代码层的体现。

## 七、虚警留痕(避免下轮重复投入)

**"未连接时参数错误返回 `(False, None)`"** —— 首轮扫描时我判定为"契约违背"
(库文档:参数非法抛 `ValueError`),复核实为**虚警**:

- 未连接且无可用传输时,`_execute` 的惰性重连先失败 → 直接返回 `(False, None)`,
  **根本没有走到参数解析**;
- 用桩传输接通后,同一批调用**全部正确抛 `ValueError`**(空地址/非法记号/位号越界/
  位软元件带位号/字类型带位号/位软元件字单位/未知软元件 7 项);
- 唯一残留的可改进点是**错误优先级**(§三 P3-1),属文档披露项,非缺陷。
