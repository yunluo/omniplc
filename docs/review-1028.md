## 二、P1:SR 时序模型与手册出厂默认相冲(亲验)

### 2.1 现状(亲验源码)

```python
# reader/keyence_sr.py:150-166
def _scan_once(self, bank, read_timeout):
    """LON → 扫码窗口 → LOFF → 读一行应答(内部方法,须事务内调用)。

    LOFF 之后才发应答,故读超时(...)时 ...          ← 注释断言"LOFF 之后才发应答"
    """
    transport.send(lon)
    time.sleep(self._scan_dwell)      # 固定 1.0s 窗口
    transport.send(SR_CMD_LOFF)
    # 应答在 LOFF 之后才发送;临时收紧收包超时
    ...
    line = self._read_line(transport, read_timeout)
```

### 2.2 手册实核(子代理逐页)

| 手册位置 | 原文 | 与本库代码的关系 |
| --- | --- | --- |
| p.47 | 「数据发送时机 **初始值 读取后发送**」+ 取值表 p.82 命令编号 **201 初始值 0** | **出厂默认是读取后立即发送**,不是"LOFF 后发送" |
| p.53 | 「读取后发送:在读取时**立即输出**读取数据」 | 明确时点 |
| p.54 | 「在解码处理完成前关闭触发输入时,**即使已拍摄可读取条码的图像,仍将变为『读取错误』**」 | **直接否证**"等 1.0s 再关"的做法 |

### 2.3 影响(两条,均为现场风险)

1. **扫描窗口可能过短**:固定 `scan_dwell = 1.0s`;若解码耗时超过 1s,LOFF 会在解码完成前关闭触发,
   按 p.54 **必然变成"读取错误"** —— 而现场会以为"没扫到码";
2. **更隐蔽的一条**:若结果在 1.0s 窗口内**已经发出**(出厂默认即如此),它**滞留在收包缓冲**,
   直到 `LOFF` 之后才被 `_read_line` 读走 —— 表面能跑通,但:
   - 每次扫描的**实际时延** = `scan_dwell` + 读取时间(白等 1s);
   - 多码/多行模式下**余下行留缓冲**,下一事务读到**陈旧结果**(与 §三 P2-3 叠加)。

### 2.4 定级与修法

- **定级 P1**:①与时序依据相冲(依据铁律面);②后果含"陈旧结果"这一**静默错值**形态;
  ③`scan_dwell` 是**对外暴露的语义**,现场会按"等 1s 再关"理解它。
- **修法建议**(两步,可分离):
  1. **语义订正(零行为风险)**:把 `scan_dwell` 的 docstring 改为
     "`LON` 之后、`LOFF` 之前等待的时长;用于适配设备侧『触发OFF后发送』配置" ——
     并**显式声明本库假设设备配置为"触发OFF后发送"**,而手册**出厂默认是"读取后发送"**;
  2. **行为(需真机裁决)**:增加"读取后发送"模式支持 —— `LON` 后**立即读**结果行
     (以结果行到达为界),`LOFF` 仅作清触发;或在构造期加 `send_timing` 参数
     (`"after-off"` / `"on-read"`)并按其切换读序。
- **真机判据(唯一能定论的方法)**:发 `LON\r` 后**立刻**读,看 1.0s 窗口内是否已有结果字节。
  若已有 → 本库当前实现**必然**少读一个窗口且白等 1s。

### 6.1 P1-A 基类字符串路径**绕开位软元件字单位门控**(亲验,影响 **MC 全族**)

- **亲验**(同一地址 `R100`/`M100`,位软元件):

  | 调用 | 结果 |
  | --- | --- |
  | `write_string("R100", "AB")` | **照发**(帧内码 `0x90`,字单位 `0114`) |
  | `read_string("R100", 2)` | **照发**(`0104` 字单位) |
  | `read_ushort("R100")`(对照) | **`ValueError`(门控拒绝)** |

- **根因**:`_MelsecMcBase._read_string`/`_write_string` **未调用** `_check_bit_device_word_access`
  (而 `_read`/`_write`/批量三路径都调了);
- **后果**:写 1 个继电器 → **静默整字覆盖 16 点**(写字符串的首字);读回 16 点合并值当字符串。
  属静默错值,且**触发极容易**(KV 的 `R` 是五设备里唯一的位软元件);
- **影响面**:原写「**MC 全族**」,**经对抗验证后需收窄为两类**:
  - **真缺口**:三菱(`M/X/Y`)、**KV(`R`/`B`)**、汇川(`M/B`)—— 实测 `write_string("M100","AB")`
    照发字单位帧,而同址 `read_ushort` 被门控拒;
  - **继承但无后果**:**松下**(`R/X/Y/L`)—— 其 `panasonic/mc.py` 把
    `_bit_device_word_access_allowed=True`(**有意**允许位软元件字访问,见 review-1025 §五#4),
    实测 `read_ushort("R100")` → `(True, 1)` ⇒ 门控放开是**设计意图**,不构成缺陷;
  - ★ **原报告遗漏的一面**:**native/async MC 同缺口**,且是**独立实现而非继承** ——
    `native/melsec.py:231-254` 的 `_read_string`/`_write_string` 同样未调门控
    ⇒ 修法须**两侧同改**(与 review-1034 §4.2 的 native/同步分叉同型);
- **定级**:对"真缺口"三族维持 **P1**(静默整字覆盖);对松下**撤销**该条;
- **修法**:在 `_read_string`/`_write_string` 补 `self._check_bit_device_word_access(parsed)`

## 七、主会话顺带核实(基恩士 MC 码表 —— 并入 §6.2 的依据链问题)

`KEYENCE_MC_DEVICE_CODES` 仅 **5 项**,与三菱表逐项对拍:

| 记号 | 基恩士 | 三菱 | 判定 |
| --- | --- | --- | --- |
| `B` | `(0xA0, 1, 16)` | `B=(0xA0,1,16)` | 一致 |
| `W` | `(0xB4, 0, 16)` | `W=(0xB4,0,16)` | 一致 |
| `DM` | `(0xA8, 0, 10)` | 三菱无 `DM`(**0xA8 是三菱 `D`**) | 语义借用 |
| `R` | `(0x90, 1, 10)` | 三菱 `R=(0xAF,0,10)`(**0x90 是三菱 `M`**) | 语义借用(且位性不同) |
| `ZR` | `(0xB0, 0, **10**)` | 三菱 `ZR=(0xB0,0,**16**)` | **同码不同进制** |

→ 与 review-1025 §8.4 的"码空间借用格局"一致;`ZR` 进制差异**需 SLMP 手册裁决**
(基恩士 KV 的 ZR 编号是十进制还是十六进制),列入 §六 待答。
